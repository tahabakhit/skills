# PR description and feedback context

Use the repository's template and actual target/diff. Do not invent a stack, draft
policy, staging branch or release process. git-hygiene owns candidate freshness and
mutation safeguards; the active delivery coordinator owns the broader endpoint.

Write a title from the final effect. Explain why the change exists, net behavior,
non-obvious decisions, compatibility/deployment/migration effects, review risks and
validation outcomes. Omit empty template prompts and claims that fit any patch.
Link the relevant issue; use closing language only when this scope resolves it.
Preserve multiline Markdown with a body file when an authorized GitHub CLI submission
needs it. A body draft is not permission to open/update a PR.

When asked to summarize feedback, distinguish verified findings from disputed claims
and pending work. For code finding adjudication, use available code-review judgment;
for implementing repairs, return to the active delivery task. Do not silently edit
code while preparing submission text, or claim fixes tested on a different candidate.

Return the requested text or observed published identity with material limits. Do
not invent version bumps, release artifacts or completion of merge follow-through.
