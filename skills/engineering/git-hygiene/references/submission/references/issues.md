Write an issue so someone can act without the original conversation. Follow the
repository's issue types, templates, labels and domain decisions before publishing.

- Title the observed symptom or desired outcome with the component's established
  terminology, not a guessed fix or a vague request to improve things.
- For a bug, give the shortest known reproduction, actual versus expected result,
  frequency, impact and relevant environment. State intermittent or unreproduced
  behavior honestly. Redact sensitive logs; separate evidence from suspected cause.
- For a feature or investigation, explain the current limitation, desired outcome,
  reason, completion conditions and material open decisions. Include implementation
  detail only when constrained or already agreed.
- Keep independently actionable problems separate. Links support context rather
  than replace it. Remove empty template prompts and generic claims.

Apply metadata only under established repository policy or user direction. An
issue request does not authorize implementation, and drafting alone does not
authorize publishing. Stop at the requested boundary.
