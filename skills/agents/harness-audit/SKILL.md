# Audit a harness

Bound the audit to the user's workflows and reported friction. Inspect current native
capabilities, active session tools and instructions, and the maintained working set
separately. An installed folder does not prove exposure; one session does not prove
an absent capability. Check project overlays before calling something missing.

Read [audit checks](references/audit-checks.md), selecting only relevant sections:

- Guidance coverage and nested instructions: ownership, scope, routing and conflicts.
- Workflow fit: material, judgment, action, presentation and continuity.
- Command visibility and presentation: useful controls versus permanent agent surface.
- Mutable contracts, delegation and review: current interfaces and evidence boundaries.
- Environment coherence: trace representative workflows across all involved layers.

Prefer keeping, trimming, merging or moving existing surfaces over adding another
skill or extension. A new owner needs a recurring consequential decision that no
existing owner covers. Do not score quality from package names or token counts.

Remain read-only. Do not install, edit, remove, reconfigure, launch experimental
sessions or mutate the troubled session as part of an audit. Existing instructions
govern access and questions; noninteractive helpers report evidence gaps.

Return evidence-backed findings ranked by effect on the user's work: observed
mismatch, current owner, proposed disposition, expected benefit/cost and validation.
Credit working capabilities. Distinguish confirmed gaps from unavailable evidence.
Stop after recommendations unless implementation is separately authorized.
